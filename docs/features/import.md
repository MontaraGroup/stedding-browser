# Feature: Import

Status: **I1–I4, I6, I8–I16, I18, I20–I23, I26, I27 built** (I27 on Windows since 0.3.0 beta 13, seen whole on a real Arc for Windows on 2026-10-24) (I13 with its test and I15 seen on a build on 2026-10-18); **I24 partial**
(BACKLOG S-129); **I25 partial** (BACKLOG S-51); **I17, I19 withdrawn**; **I5, I7 planned**
(BACKLOG S-103). Dia and Safari's export file (BACKLOG S-101): **I28–I32, I34–I42 built**,
written with their tests on 2026-10-25 and released in 0.3.0 beta 16, their tests passing on
the Mac (2026-10-26) except I28's `ChromiumFamilyImporterTest.FindsDiaInEitherWindowsPlace`,
which did not run there; **I33 a gap**; the Settings and command bar rows of I32 and I41
planned.
Owner docs: `docs/PRODUCT.md` §1, `docs/ROADMAP.md`. Patches: 0026 (I1–I12), 0032
(I13–I16), 0033 (I17–I20), 0038 (I6, I21–I23).

An Arc user opens Stedding and gets their sidebar back: Spaces with their icon and
colour, the essentials row, the pinned runs, folders with nesting, and the unpinned
tabs — read from Arc's own `StorableSidebar.json`, summarised before anything is
applied, inserted unloaded so a big sidebar costs nothing until a tab is opened.

A Dia user, and anyone with the file Safari exports, gets their bookmarks, history and
saved passwords in the same way: summed up first, brought in by one button, counted in
one result line, and never twice (I28–I42).

## Dia and Safari's export file

Dia is a browser built on Chromium that keeps Chromium's own files, so its bookmarks,
history and passwords are read as Arc's are (I22, I23, I27). The reader takes a table of
such browsers; Dia is its one entry. Safari 18 and later writes its bookmarks, history,
passwords and payment cards into one archive with File › Export Browsing Data to File;
Stedding reads that archive, or the folder it unzips to, on macOS and on Windows.

## Notes

- History and passwords (I22, I23) are read from copies made in a temporary
  directory — Arc keeps the originals under SQLite's exclusive lock while it
  runs, and a hot journal copied beside the file rolls back on open — on the
  thread pool, and written on the UI thread through `HistoryService` and the
  profile password store, the two calls Chromium's own `ProfileWriter` makes.
  The keychain password is asked for on the same pool thread, so the macOS
  prompt does not block the window. Nothing leaves the machine; the copies are
  deleted when the read ends.
- The Arc file on a real Mac (looked at for its shape only, never copied into the
  repo): `sidebar.containers` holds two entries, one `{global: …}` and one with
  `spaces`, `items` and `topAppsContainerIDs`; `spaces` and `items` alternate a
  string id and a dict; item `data` is one of `{tab: {savedURL, savedTitle, …}}`,
  `{list: {}}` and `{itemContainer: {containerType: {spaceItems: …} | {topApps: …}}}`;
  containers have no parent and list their children in order; a Space's
  `containerIDs` reads `["unpinned", id, "pinned", id]`. The test fixture is a
  synthetic file in that shape.
- Every tab is inserted through a restored navigation entry, the way session
  restore creates tabs it does not load: the row shows the saved title, the page
  loads on the first activation, and `WasDiscarded` gives it the slept look
  (tabs R4).
- Idempotence (I12) keys on Arc's item ids: `stedding.import.arc_ids` lists every
  id brought over and `stedding.import.arc_spaces` maps an Arc Space id to the
  Stedding Space it became, so a re-import after Arc gained a tab adds that tab
  to the right Space and nothing else. A Space deleted in Stedding stays deleted:
  its id is still remembered. `stedding.import.arc_folders` maps an Arc list's id to
  the folder it became, so what Arc adds to the list later goes into that folder, and a
  list whose folder the user removed stays removed.
- A folder inside Arc's pinned section becomes a folder whose tabs are plain
  (not Space-pinned); a list with no tab of its own cannot be made (a folder
  needs a tab), so its sub-lists come out beside it.
- The bar's Import from Arc row appears once the browser has learned the file exists:
  the first window with Spaces asks off the UI thread, so only a bar opened before
  that answer comes back lacks the row.
- Backups (I18, I20) are the plan written in Arc's own shape, so one parser serves
  Arc's file and an exported Space. A file Stedding writes names Spaces by their ids,
  tabs by their tab tokens and folders by their own ids, all of which survive a restart
  (`sidebar-file.md` Sf2); the importer treats a Space it already holds as that Space
  and skips a tab or folder that is open now, which is what makes an import a merge. A
  tab's user-given name comes back as its title, not as a name.
- Dia and Safari's export (I28–I42) are read on the thread pool and written on the UI
  thread through the profile's bookmark model, its history service (on the history
  database's own thread, for I30's check) and Chromium's password importer. Dia's files
  are copied into a temporary folder that is deleted when the read ends. Safari's file is
  read where the user chose it. Nothing an import reads leaves the machine
  (`docs/PRIVACY.md`).
- What Dia keeps where comes from a report of its Mac release, not from a real install:
  the Mac folder, the "Default" and "Profile N" layout and the "Dia Safe Storage" item.
  The Windows folders, the process names and whether Dia seals Windows passwords "v20"
  (which no other program can read) are guesses until a person with Dia installed looks.
- The 32 MB bookmarks and 64 MB history-file limits are design values, not measured on
  real exports.
