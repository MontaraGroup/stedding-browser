# Feature: Auto-archive

Status: **A1–A6, A8, A11, A12 built** (A8's "Leave site?" Stay case has its test since
2026-10-18); **A7, A9, A10 partial**: built before, each with a part written 2026-10-18 whose
tests have not yet run (A7: the Archived row's quiet shade, sidebar Y27; A9: the session's
mark on a row and in the filter; A10: no row for a tab the relaunch reopened); **A13, A14,
A15 partial**: written 2026-10-18, tests not yet run (the tabs of a window the next launch
opens again are not rows, an app's window is never one, and ⇧⌘T and Recently Closed pass over
a window a launch reopened; the cases still open are in A13's and A15's rows).
Owner docs: `docs/PRODUCT.md` ("Unpinned Tabs — auto-archived when idle"). Patches: `0011`;
A7–A11: `0028`; A6's Never default and its 7-day choice: `0060` (beta 14).

Once the user has chosen a time (nothing is archived until then, A6), unpinned tabs that
nobody has looked at for that long leave the sidebar on their own, the way Arc's do.
"Archived" means closed into Chromium's recently-closed list, so ⇧⌘T and the
History menu bring one back with its navigation intact. Nothing pinned, nothing in a folder
and nothing the user is looking at or using is ever archived (A12).

The sweep is a per-window `TabArchiver` (`chrome/browser/ui/archive/`), a timer that runs
every five minutes and closes every tab whose idle time is past the threshold (A1). The idle
time is wall-clock time, kept with the tab in the session, so a night asleep and the time the
browser was closed count, as they do in Arc.
The threshold is the profile preference `stedding.archive.idle_hours` (default 0, Never,
which turns the sweep off), set in chrome://settings/stedding, the
command bar's cycling row or the welcome flow's behaviour step (A6).

## Notes on the archived view (A7–A11, A13–A15)

- The archive is Chromium's recently-closed list, read through one function
  (`ListArchivedTabs`) that keeps TAB entries within the retention, newest first.
  A tab closed with ⌘W is in it too, shown as "closed"; the sweep's and Clear's
  tabs say "archived" and "cleared" from the mark they carried. A window, split
  or group closed whole is listed tab by tab (A9, BACKLOG S-187), except a window
  the next launch opened again (A13) and an app's window (A14).
- The mark is a `WebContentsUserData` set a moment before the close;
  `BrowserLiveTabContext::GetExtraDataForTab` takes it while Chromium records the
  tab, beside the Space's data. Nothing clears it when the close call returns with
  the tab still in the strip: that is a close waiting on the page's unload
  handlers, which is recorded when they have run.
- A13's mark is set as the window closes (`NextLaunchReopens`, held around
  Chromium's `BrowserClosing` in `UnloadController::OnWindowClosing`), from what
  the session will do with that window: a quit, an exit or a restart stops the
  session services before it closes the windows, so every one comes back (`1`);
  any other close leaves the session a profile's last window to restore, counting
  the profile's normal and little windows that session restore keeps, and not
  those already closing all their tabs (the session's own closing windows). That
  last window's fate is known only later, so its mark (`last`) is settled by the
  next window of the profile, made in this run (`SettleLastWindowCloses`, called
  from `BrowserWindowFeatures::InitPostWindowConstruction`, just after the
  session's `WindowOpened`): if the session is restoring its last session then,
  into that window or into windows of its own, the closed window is coming back
  (`1`); otherwise the session has committed the close, and the mark goes. On
  the Mac a window from the Dock or the menu bar is of the second kind; off the
  Mac a new window with no other window of the profile open is usually of the
  first. A run that ends with the mark still `last` has reopened the window at
  the next launch, which reads it from the list's file and treats it as `1`.
  The mark is written at once rather than at the run's end so that a run ending
  in a crash, which runs no shutdown code, leaves it on disk too.
- The crash bubble's Restore (`SessionCrashedBubbleView`, after
  `SessionRestore::RestoreSessionAfterCrash`) marks the windows Chromium read
  from the crashed session at its load (`MarkTheCrashedSessionReopened`): they
  are the list's windows with no close time and no id from the list's own file.
  A window of an earlier crash that nobody restored is read from the file by
  then and keeps its rows.
- Not mirrored: a profile that must sign in again keeps every window it closes
  and restores them all at the unlock, whatever the startup setting; those
  windows are not marked, so their tabs are rows beside the reopened ones. Only
  force-sign-in profiles get there.
- Records written before this build carry no mark: the windows of earlier quits
  stay rows until the retention passes (30 days by default) or Clear archive.
  Clear archive deletes the marked windows too: the page does not show them, and
  their tabs are open, so nothing the user sees as closed is lost.
- The window itself stays in Chromium's list. In Chrome, ⇧⌘T straight after a
  relaunch opens a second copy of it; here ⇧⌘T, the menu bar's Reopen Closed Tab
  (and whether it is enabled with no window open), both Recently Closed lists and
  the Windows taskbar's Jump List pass over it (A15, `NextLaunchReopened` and
  `MostRecentClose` in `closed_folder.h`, beside the folder closes those menus and
  ⇧⌘T already read there). Chromium's own list API is unchanged, so an extension
  calling `chrome.sessions.restore()` with no id still gets Chromium's most recent
  entry. Two lists still show the reopened windows, and group no folder close
  either: Linux's global menu bar (`dbus_appmenu.cc`) and the Recently Closed of
  the app menu built from actions (`RecentTabsBuilder`, behind a feature that is
  off by default).
- A13's mark is a guess made at the close (or, for `last`, settled by the next
  window). The next launch settles it (`SettleWhatTheLaunchReopened`, from
  `SettleLastWindowCloses`, after that launch's session restore and once the list
  has loaded), once, and only for records read back from the list's file, so a
  window an earlier launch reopened stays `1`. A launch that does not restore
  the session after all (the Mac launched hidden at login and then given a window
  from the menu bar, a change of the startup setting between the close and the
  launch, a session file that cannot be read) leaves the quit's windows as rows,
  ⇧⌘T's and in Recently Closed, as closed windows (BACKLOG S-230). Betas 18 to 20
  wrote `1` at a quit, which reads as settled: the first launch after updating
  from them, if it restores nothing, leaves that quit's windows out once.
- An app's window (web apps Wa12) is recorded as a window when it closes, as
  Chromium records it for ⇧⌘T, which brings it back as the app's window. The
  archive lists none of its tabs (A14): its pages are the app's, never tabs of a
  Space, and its Restore would have put one into a browser window outside the
  app's jar. So a relaunch that brings an app's window back (an update,
  chrome://restart) needs no A13 mark for it: A13 marks normal windows alone, and
  the app's window was never a row. ⇧⌘T after such a relaunch still offers the
  app's window, as Chrome does.
- The folders go under the archive's own key, not the session's
  `stedding.folderpath`: under that key a ⇧⌘T would park the path on the tab and
  the next session restore would build a second folder with the same id. So ⇧⌘T
  brings a tab back without its folder; the archive's Restore puts it back in the
  folder when that folder is still there.
- The page is plain DOM (no Lit), like the welcome flow: the keyboard and VoiceOver
  come from real inputs and buttons. It refreshes on the service's own change
  notification, so a restore or a sweep in another window shows at once.
